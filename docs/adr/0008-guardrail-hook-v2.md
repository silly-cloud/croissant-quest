# 0008 Guardrail hook v2: fail closed, shell-aware parsing
Status: accepted. Supersedes the "Claude Code guardrail" section of 0007 (the Husky part of 0007 stands).

## Threat model
The hook is a tripwire for a well-meaning agent that is about to make a destructive mistake. It is not a security boundary: a determined process can always get around a text check (scripts, aliases, variables, the GitHub API). The real boundary is GitHub branch protection or a ruleset on `main` (require a PR and the `check` status, block force push and deletion). The 2026-10 audit found `main` unprotected; the owner should turn that on.

## What changed from 0007
- **Fails closed.** `.claude/settings.json` still runs `"$CLAUDE_PROJECT_DIR"/.claude/hooks/block-dangerous-git.sh`. That file is now a builtins-only `/bin/sh` wrapper. It exits 2 if `node` is not on PATH, if `guard.mjs` is missing, or if `guard.mjs` exits with anything other than 0 or 2 (a crash). `guard.mjs` exits 2 when stdin is empty, is not JSON, or has no string `tool_input.command`, and when nesting is deeper than 16 levels. The message says "guardrail could not check this command ... ask the user".
- **No jq.** The parsing and matching live in `.claude/hooks/guard.mjs` (Node 22, no dependencies). The repo needs Node anyway.
- **Shell-aware.** A real lexer resolves quotes, `$'..'` and backslash escapes, so `git push "-f"` is seen as `-f`. It splits on `; && || | & ( )` and newlines. It recurses into `$(..)`, backticks, `<(..)`, `sh/bash/zsh -c` payloads (also `-lc`, `-ec`), `eval`, here-strings and heredocs fed to a shell, `$(..)` inside unquoted heredocs, `env -S`, and `git config alias.*` values. Heredoc bodies fed to other commands are data, so `cat <<X` text no longer over-blocks. Words in `-m/-F` values and in echo/printf arguments are data. The check works on parsed argv, not on substrings.
- **Normalisation.** It strips env assignments, `env`, `command`, `builtin`, `exec`, `nohup`, `sudo`, `doas`, `time`, `nice`, `timeout`, `stdbuf`, `xargs`, `npx`, `pnpm/npm/yarn exec`, and reserved words. `\git`, `"git"` and `/usr/bin/git` all resolve to git. Git global options (`-c k=v`, `-C dir`, `--git-dir`, `--work-tree`, `--no-pager`, `--exec-path=` ...) are skipped. Long options match on any unambiguous prefix, as git itself does (`--forc` and `--force-w` count as force).
- **Policy additions** (the owner's rules): force push in every form (`-f` in any short cluster, `--force*` and its prefixes, `+refspec`, `--mirror`, `--prune`, and also `--dry-run --force`); `push --delete/-d`, `push origin :ref`; a push whose destination is `main`/`master` (also `HEAD:main`, `x:refs/heads/main`, wildcard destinations, `--all`); `reset --merge/--keep`; `checkout -f`, `switch -f/--discard-changes`; `stash drop/clear`; `tag -d`; `update-ref -d`; `filter-branch`, `filter-repo`; `rebase` (except `--abort/--quit`); recursive `rm` (with or without `-f`) of `.git`, `/`, `~`, `$HOME`, `.`, `..`, `*`, or the repo root or any of its ancestors; `find <same targets> -delete`; `git config` aliases that run a blocked command; any write to `core.hooksPath` (also `-c core.hooksPath=`); `--no-verify` on commit, push and merge, `commit -n`, `HUSKY=0 git commit|push|merge`; dangerous git subcommands run under `xargs` (their arguments are unknown); text piped into a shell with no `-c`.
- Still allowed: `git push`, `git push [-u] origin <branch>`, `git push origin HEAD`, `push -n` (that is `--dry-run` for push, not `--no-verify`), `reset --soft`/`--mixed`/`reset HEAD file`, `branch -d`, `clean -n`, `stash push/list/apply/pop`, `commit --amend`, `merge --no-ff`, `HUSKY=0 pnpm install`, `rm -rf node_modules` and other paths inside the repo or under `/tmp`.
- **Speed.** One Node process, linear lexer. 5000 segments take about 60 ms (v1 took 60-70 s).

## Exit 127 and other non-blocking failures
Claude Code blocks only on exit code 2. Every other non-zero code, including 127 (command not found) and a hook timeout, is a non-blocking error, so the tool call goes ahead. For that reason:
- The settings command stays the absolute `"$CLAUDE_PROJECT_DIR"/.claude/hooks/...` path, not a bare or relative name. The wrapper uses only shell builtins (it needs no `dirname` or `jq` from PATH) and turns a missing `node` or `guard.mjs` into exit 2. A plain `node guard.mjs` in settings would give 127 without node, and exit 1 without the file. Both would be non-blocking.
- The one gap left: if the wrapper file itself is missing (for example, a worktree checked out at a commit from before the hook existed), the shell returns 127 and the hook does not block. No hook command form can avoid that. Branch protection covers it.
- No `timeout` is set, so the default applies. A shorter timeout would only make the fail-open timeout path more likely.

## Known residual gaps (out of scope by design)
Git alias invocations are not resolved (`git p` after an alias was defined elsewhere). Also not caught: script files (`bash s.sh`, `source`, `. s.sh`); commands built from variables (`$GIT push -f`, `git push $(echo -f)`); `bash -c 'git "$@"' _ push -f`; `xargs rm -rf` (targets come from stdin); `git branch -M`, `worktree remove --force`, `reflog expire`, `gc --prune`; `pull --rebase`; other tools such as `gh api -X DELETE`, ssh, and git through other languages (node, python). `GIT_CONFIG_*` env config is not checked either. Branch protection is the answer to all of these.

## Test
`bash .claude/hooks/test-guardrails.sh` needs only bash and node. It covers the policy, the audit's bypass suite, the allowed list, fail-closed cases (empty, non-JSON, truncated, array, missing fields, PATH without node or jq, missing or crashing `guard.mjs`, nesting too deep), the message wording, and a 5000-segment performance check. It prints `SUMMARY total=.. blocked_ok=.. allowed_ok=.. failures=0`.
